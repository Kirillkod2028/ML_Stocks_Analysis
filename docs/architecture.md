# Архитектура ML Stocks Analysis

## Поток данных

1. Асинхронный клиент получает историю торгов, дивиденды, IMOEX, USD/RUB и RVI из MOEX ISS.
2. История очищается, сортируется и проверяется на дубликаты.
3. Цены корректируются на корпоративные события. Основной пайплайн обнаруживает крупные разрывы, похожие на сплиты, и приводит прошлые цены к сопоставимому масштабу.
4. Для каждого тикера рассчитываются признаки и пятидневная целевая переменная.
5. Тикерные таблицы объединяются в панели рынка и секторов.
6. Панельные признаки winsorize- и rank-нормализуются по дате. Тикерные признаки нормализуются rolling z-score.
7. Обучение использует sklearn Pipeline: imputation, scaling и estimator.
8. Optuna подбирает гиперпараметры по Spearman IC на временных фолдах.
9. Финальные bundle-файлы сохраняют pipeline, список признаков, параметры и идентификатор датасета.

## Границы модулей

- `src/ml_stocks_analysis/data_pipeline.py` — загрузка, очистка, feature engineering, target и запись parquet.
- `src/ml_stocks_analysis/training.py` — обучение по `datasets/`.
- `src/ml_stocks_analysis/training_processed.py` — обучение по `data/processed/`.
- `scripts/` — стабильные пользовательские entry points.
- `legacy/` — предыдущая версия сборщика без актуальной обработки сплитов.

## Каталоги артефактов

- `datasets/` — первоначально сформированные датасеты.
- `data/processed/` — очищенный вариант и metadata.
- `models/` и `models_processed/` — сериализованные bundle-файлы.
- `results/` и `results_processed/` — метрики, таблицы и графики.

## Технический долг

Главный технический долг — крупные модули с дублированием между обычным и processed-пайплайнами. Следующая итерация должна вынести общую конфигурацию, загрузку данных, признаки, CV и модельный registry в небольшие тестируемые модули. Это лучше делать отдельным изменением с regression-тестами, а не одновременно с перемещением файлов.
